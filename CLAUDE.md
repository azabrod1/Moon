# CLAUDE.md

Guidance for coding agents working in this repository. Claude Code reads this file directly; Codex reads it through `AGENTS.md`, a symlink to this file. There is one copy to keep current, and it is this one.

## Build & Development

```bash
npm run dev        # Vite dev server (hot reload)
npm run build      # TypeScript check + production build (dist/)
npm test           # vitest — astronomy + planetarium unit/golden tests
npm run gen:moons  # Regenerate satellite elements + goldens from JPL (--offline uses .moon-data-cache/)
npm run gen:maps   # Regenerate derived texture maps (runs in headless Chromium)
npm run gen:ktx2   # Regenerate the GPU-compressed colour rungs — 23 jobs, 9 UASTC (planets + Earth) and 14 ETC1S (the photo moons); run BY NAME, not --all (bundled basisu; a shipped webp, sharp, or a gen:moonmaps intermediate per job)
npm run gen:tiles -- <job|--all> [--verify | --grey]   # Re-cut sector tile sets + rewrite sectorSets.generated.ts (needs `npm i --no-save sharp@0.35.4`); --grey only checks the one-channel mask sets are grey texel for texel
npm run publish:tiles -- --root=<tiles root> --repo=<tiles repo checkout>  # Copy verified sets into the tiles repo (never pushes)
npm run gen:cloudmaster [-- --dry-run | --pictures-only]   # Assemble NASA's 21600 cloud hemispheres into the 43200x21600 cloud master (.moon-data-cache/levels/earth-clouds.v2.43200x21600.r8 + .json report) with NASA's infrared polar layer and the shipped sheet's grade, plus a page of side-by-side pictures (needs `npm i --no-save sharp@0.35.4`; cuts no tiles or rungs)
```

## Architecture

A Three.js WebGL app. The **Planetarium** (`src/planetarium/`) is the app: the full solar system in real units (1 scene unit = 1 AU) on a floating-origin pattern (player stays at scene origin, bodies are offset by the player's position). `src/main.ts` is a thin entry point owning the renderer, composer, cameras, mode switching, and animation loop; each mode is a controller exposing `activate()/deactivate()/update(dt)`. The renderer's tone curve is the switch's to set (`src/app/renderProfile.ts`: Neutral for Look inside, ACES for the rest, applied beside the composer each branch builds) — a mode never writes it for itself, because main caches every mode and disposes none, so a curve set for a mode's life was the app's for the session. `src/interior/` is the Look-inside tool: `data/interiorTypes.ts` is the interior-model schema, `data/models/*.ts` the provisional models (every number sourced; `data/validate.ts` pins the authoring rules and `data/interiorRegistry.ts` answers for every catalog body with a coverage state and a bulk line; a region's only say in how its material is drawn is a small `look` — a hue turn, a saturation and a lightness on its family's palette, `data/artParams.ts` — so a crust reads pale and grey without a palette of its own), `evidenceSummary.ts` the one place the evidence is read into words — a standing per claim from the KIND of evidence (observed, inferred, contested…), never a score; there is deliberately no points rubric anywhere — and `ui/evidenceView.ts` the grouped reader-facing view of a region's evidence, `cutFrame.ts` the cut itself (one quarter wedge through every layer at Cutaway, one disc at Section; it FACES THE CAMERA by default — the cut is a diagram, and a body-locked cut seen from the side, below or behind shows a half section, a crease or nothing — so orbiting turns the body under a cut that stays put on screen, and the "Cut faces the camera" row in View options, off, is the body lock, a cut chosen once and held to the body's pose through a body-space anchor, for anyone who wants a cut in a solid; Reset view returns to the entry pose and chooses the cut afresh there; the wedge is yawed 20° so one face meets the eye, a yaw that fades to nothing as the opening widens to Section, because a disc turned off the camera shows the skin's far half past its edge; the studio's lens is LONG, 12° (`interiorLayout.STUDIO_LENS`, with the zoom as a ratio to the fit), because the hinge is the camera's up and its ends sit at the disc's centre depth while the disc's edge lies asin(R/D) ahead of them — at 40° the faces' rims rose a dozen pixels past each end and every cutaway read as two lobes with a crease, top and bottom, which no lean can cure and which the test on `hingeEndRisePx` pins at under a pixel and a half), `rendering/skinCut.ts` the discard that removes the skin, the rings, the air shell and the Sun's photosphere inside the wedge — the wedge as the pair of half-spaces its faces bound, linear at the hinge where an angle test left a notch at each pole, and a far-side shell reflected through the plane facing the camera THIS frame, since the wedge does not follow the camera — `interiorPick.ts` the CPU pick that mirrors the wedge the shaders draw, `ruler.ts` the depth ruler's layout through the same remap (one straight line down a face, hidden once both faces turn away) and `ui/DepthRuler.ts` its drawing IN THE PLANE OF THAT FACE (every mark measured along the face's own axes and projected, each label transformed by the face's projected axes at its anchor, so the ruler foreshortens with the face instead of floating over it; the km labels thinned as a series — every second, fifth or tenth tick — with the unit on the deepest, a label dropped from a core too small to hold it, and an annotation bracket drawn only with its name inside the disc; `ui/rulerLabels.ts` holds those rules pure), `interiorTransition.ts` the ceremony's lengths and its order in one place (the entry's opening, a swap's close, the skin's dissolve, the reopen, and whether the cut waits for the veil — it does: activate resolves with the body presented and the cut closed, main lifts the veil onto a frame the studio has actually drawn, and its `transitionend`, or the timer standing in for a lost one, opens the cut, so the whole opening is seen instead of half of it playing behind black), `interiorLayout.ts` the stage-aware framing (the body fitted to the rectangle the strip and the panel leave free — the bound is `InteriorScene.boundRadius`, the body with its air and never its rings, which run off the stage as context — the zoom kept as a ratio to the fit; the fit is taken again once a body is presented, since the air shell's scale is only known then and the Sun's corona reaches 1.3 radii), `temperatureProfile.ts` temperature as a function of physical radius — the ONE sampler the Temperature diagram, the Materials glow, the body's scale, the legend swatches and the inset read, so the two views never disagree about how hot a place is; the faces hold each region's ramp as knots and compute the incandescence per pixel from the local temperature (a star's zones read that place pulled part way to their region's, so they step at their boundaries the way a diagram draws shells), and `rendering/sectionMaterial.test.ts` holds the GLSL to the TypeScript — `temperatureScale.ts` the body-specific scale the faces and the legend share (log when the range is wide; a single known value is a scale of one value, never no scale), `rendering/outputTransform.ts` what the output path does to a diagram face (the exposure, Neutral, sRGB), stated once so the sweep verifies it on the real renderer, `ui/hoverCard.ts` the preview beside a fine pointer, built once and moved by a transform, with the mode keeping a pointer's moves for the frame so a burst is one pick (the card and the mode both cache on its key, so the key carries the body and the model in front of the region — `hoverCardKey` — because a bare region key is shared: a dozen models call their innermost region 'core'), `ui/interiorCopy.ts` the panel's recurring labels, and `ui/InteriorPages.ts` the panel's pages (a pin opens a region's summary; its details, its evidence and the model page are pages of the same host on both breakpoints — the sheet on a phone, the side panel on desktop — with the layer list the page they return to; the rarely touched controls sit behind View options in the strip along the top). Temperatures show in ONE unit, the reader's (kelvin by default, celsius from View options, session-only). In Temperature mode a region whose temperature nobody knows is hatched, never drawn cold, and on desktop says so under its name on the ruler (`ui/interiorCopy.TEMPERATURE_NOT_KNOWN`), so the hatch is never read as a texture. The studio (`InteriorScene.ts`) borrows the planetarium's skins, air shells, rings and the Sun's photosphere (held under the bloom threshold there, over a floor of its own colour, so the core is the one thing that blooms), all cut by the same frame (`rendering/skinCut.ts`); its key is camera-relative from the upper left and the section faces carry a fill of their own inside the shader, from the right and in the key's units, so the face the key misses is lit from its own side and never a scene light the skin would see; a body swap is a ceremony (close, cross-fade in the skin's shader, reveal with a ghost) and `prefers-reduced-motion` stills all of it. `src/moonFlight/` is a dormant lunar-landing mini-game — intact but with no UI entry point. `src/astronomy/` is the ephemeris (Meeus + Standish elements, every planet's moons, analytic shadow/eclipse engine). `src/shared/` holds framework-free helpers (`math/angles` is the single source for `DEG2RAD`/`RAD2DEG`).

**Module headers are the subsystem documentation** — read the header comment before changing a module. Pure logic lives in DOM-free modules with colocated tests; the tightly-coupled per-frame core deliberately stays in `PlanetariumMode.ts`.

Generated / transcribed sources: `src/astronomy/satelliteElements.ts` is generated — edit only via `npm run gen:moons`; `standish.ts` element values are transcribed verbatim — never re-round them. The bright-star catalog ships as `public/stardata/bright-stars.v1.bin` + its golden `brightStarsGolden.json`, both written only by `npm run gen:stars` (parser and store: `src/planetarium/data/brightStars.ts`; consumers read `brightStarCatalog()` only after the boot loader installs it).

**Frame contract: right-handed J2000 everywhere.** The scene is the J2000 equatorial frame as a proper rotation: +X vernal equinox, +Y celestial north, +Z = RA 270°. `raDecToVector` (`planetary.ts`) is the single chirality definition site — never re-inline the formula. Meeus Earth/Moon longitudes (ecliptic-of-date) precess to J2000 at the `planetary.ts` vector seams — never inside `ephemeris.ts` (its goldens quote of-date values). Earth's render position stays Meeus (−Sun vector, precessed) for exact Sun–Earth–Moon coherence. Absolute rotation phase is real (IAU pole + node + verbatim W). All sign conventions are deliberate and test-pinned: don't flip any in isolation. JSON goldens are stored in raw Horizons frames; only the test-side `horizonsToScene` mappings encode the scene convention.

**Lens correction**: the planetarium renders through a stereographic lens pass (`shared/math/lensProjection` + `app/LensPass`), so:

- `applyDesignFov` is the only legal `camera.fov` writer; `camera.fov` holds the overscan — never compare against it, use `displayFovDeg()`.
- On-screen sizes/footprints come from `projectSphereToScreen`; screen-authored GPU primitives pre-distort via `shared/three/lensShader` — never size them from `camera.fov`.
- Every consumer reads `lens.effectiveStrength ?? lens.strength`, never the raw request.
- `tools/oval-probe.mjs` is the asserting regression battery.

### Key patterns

- **All textures bundled locally** in `public/textures/`, referenced via `import.meta.env.BASE_URL + 'textures/'` — such paths are invisible to both tsc and Vite; verify them by running the app.
- **UI is vanilla HTML** in `index.html` (no framework); the TS reads elements by `id` — keep the `index.html` id set and the `getElementById` calls in sync.
- **Nothing half-loaded is ever shown**: a moon never renders before `MoonPainter` finishes it, and teleports hold the arrival veil until the destination is ready. Perf work must preserve this gate.
- **Transient overlays are one-modal-at-a-time** (the ☰ menu, the deck, and the Look-at menu close each other; landing, takeoff, and mode deactivation close them too) — wire new overlays into the same close calls. The tutorial card is the one deliberate exception: the tutorial stages scenes through the other overlays, so only its own buttons and lifecycle close it.
- **Space is the pause**, everywhere the ship takes keys — in cruise, over the map and on the ground: the clock stops and the ship is held with the world (`timeState.paused`; `player.held` follows it every frame and the throttle state survives untouched, so resume continues exactly as left), the same freeze the ☰ menu lays over the scene while it is open. Space no longer toggles thrust; a standstill with the clock running is S or the − button, which cut the throttle to exactly zero. The one on-screen word for the freeze is the Paused badge (`planetarium-pause-badge`, `src/planetarium/ui/PauseBadge.ts`, a button that resumes; when it shows is `ui/pauseBadgeLogic.ts` — never in surface view, whose transport strip says PAUSED already, nor under Help, a mission or the tutorial), refreshed from `updateTimeUI` on every clock write and the 8 Hz pass.
- **UI idioms**: body tints come from catalog `color` (`planetData`/`moonData`), never hardcoded; names render through `bodyDisplayName` (deck rows deliberately show raw catalog names); list rows reuse the deck's `pk-row` family; view sub-states (surface view, orbit details) are session-only. UI copy is plain and human — read the neighbouring strings and match them.
- **The mobile breakpoint is 640px**: test UI changes at desktop and at 390×844 — the narrow band is where overlays collide.

The phone heat claim (halved GPU work when parked, not halved heat) is a USB soak and is not measured here. `__moon.quality()` reports the level, the rung, the bounds, the bytes, the allocation and the decision rule's own window, `__moon.setQuality(level)` picks a level exactly as the menu row does, and DEV `__moon.quality({inject})` feeds synthetic frame intervals straight to the rule, so a browser run can prove a rung moves without faking load — which no pin can do, a pin holding the rule idle by design. `__moon.perfTargets()` answers with `sceneAlloc`, `sceneDraw`, `sceneViewport` per target, `uvScale` and `sceneBytes` from the ALLOCATION, so "did it draw fewer pixels" is read off the draw size and "what is the device holding" off the allocation — and so does the `?debug=1` memory line; `?nightsides=real|brightened` (any build) boots at that Night sides value, the one control on the ☰ **Display** page (the tier after Graphics; the root row reads `Real nights` / `Brightened nights`): Real is the default and the physics — a night side is black where no sunlight falls, with planetshine and the air's twilight still drawn — and Brightened lifts every planetarium body's night half to its own albedo times `NIGHT_LIFT_STRENGTH` (`world/surfaceShading.ts`), joined by max() to the starlight floor and the sky's ambient, night-weighted like the floor and killed with it in a silhouette. Brightened also stands the night-side exposure rule down (`?nightexposure=0`'s rule, `world/nightExposure.ts`): the frames it is for are the ones with daylight in view, where that rule would take the dark side's own light away again, so while it is on every body's slot is 1 and the lift never takes the factor at all. The lift is ONE uniform object (`nightLiftUniform`) that PlanetFactory points the planetarium's globes, their sectors and decks, and the moons at before their first compile; Look inside, How many fit? and the warm-up probes build their surfaces with a zero of their own, so no mode switch has to touch it. The URL wins over the saved value, which is its own localStorage key (`src/app/nightSidesSetting.ts`), never the journey save; it is a user's setting, so it is not a perf switch and the sweep never touches it; `?tiles=<url prefix>` (DEV only) fetches sector tiles from somewhere else — rarely needed now that `npm run dev` also serves the staged levels in the main checkout's `.moon-data-cache/tiles-staging` on its own origin (`tools/devTilesPlugin.mjs`; `MOON_TILES_ROOT` moves the root), so a plain dev URL streams every level; `?envelope=<MiB>` (DEV only) shrinks the shared GPU memory envelope, which is how a desktop is put under a phone's pressure without a phone (the profile's ceiling and sector floor stay put); `?perfoff=<key,key>` (DEV only) boots with those GPU-efficiency switches off (`src/app/perfSwitches.ts` — every switch is an A/B against the picture as it was, flipped live by `__moon.perfArm(key, on)`; this is how one whose state is fixed at upload, `r8-maps`, or at compile, `cloud-program`, is captured in its old state; the four `cloud-probe-*` keys are not switches but probes — each takes one term off the cloud deck so a device can price it, off by default, never exact, and a production build carries neither reading; `cloud-noise-frame` is a VISUAL key — a fix that ships on and changes the picture on purpose (the deck's close-range detail read on the deck's own sheet, `bodyToDeck` in `world/cloudDeck.ts`, rather than in the world's axes, where it stood still in the sky while the cloud turned and drifted under it), whose OFF arm is only the control: never exact, never in the combined row or the Phone preset); `?glint=<roughness>[,<keep>[,<cap>]]` (DEV only) draws open water at that GGX roughness for the session, with the mirror term's keep and cap after it — the ocean glint's three authored numbers (`OCEAN_ROUGHNESS`, `OCEAN_SPECULAR_KEEP`, `OCEAN_GLINT_CAP` in `world/surfaceShading.ts`), live as `__moon.glint({roughness, keep, cap})` so a look round is a sheet from one page load rather than an edit per candidate; `?haze=<clear view>` (DEV only) shows that much of the air's haze in every direct view of a surface for the session — the authored number is `SURFACE_HAZE_CLEAR_VIEW` in `world/surfaceShading.ts` (Earth 0.35; 1 is the physics, and the horizon carries the whole column whatever the number, so the limb meets the shell as baked), live as `__moon.haze({clear})`; `?perf=1` (DEV only) raises the on-device perf sweep (`src/app/devPerfSweep.ts`) — an overlay that measures, at whatever pose the app is parked at, what one layer at a time costs. **It is built around a device that heats under its own measurement and caps its frames at 60**: every candidate is measured in A B B A blocks (baseline, candidate held across two windows, baseline) with 2.5 s holds and the first 0.5 s dropped, each candidate hold charged against the baseline hold beside it, and the row shows the median of those pairings with their spread — a spread wider than the median is a device that moved more than the switch did. The order is reshuffled every run and printed, the all-off control sits outside the blocks, and every baseline is printed in sequence as a thermal-drift line (a fixed-order single-pass sweep ranks the order, not the configurations: an iPhone run read the spacecraft at 30 ms, which was the drift). **The load amplifier pins the render ratio to 3 for the run** — a checkbox turns it off — so every configuration sits below the 60 cap, where a 2–4 ms saving has somewhere to show instead of reading 60 either way; the milliseconds are then ratio-3 milliseconds, and the bloom chain sizes from the display's own ratio rather than the pin, so the bloom rows are at their true size. The run is frozen (clock rate 0, restored after; sector tiles waited out before the first hold; a page hidden mid-run — Auto-Lock — stops it on the spot and says so) and the pose is left where it is — the verdict names it (read from the close-range density map, else from the body the ride frame holds, else it says why not), daylight, terminator or night with the Sun's height under the camera, because an early-out that skips work where a term is exactly zero cannot be priced from the wrong side of the terminator. Four runs, each stating its holds and wall time before it starts: **Phone** (the preset — the efficiency switches plus the tile layer, half the pixels and everything-at-once, one block each, about two minutes; the default on a touch device), **Sweep** (every candidate, two blocks each), **Quick** (the older single bracketed pass, A B A C A D at 3 s) and **Soak** (five minutes of baseline logged every ten seconds, which is the only run that can say whether a saving survives sustained load). The candidates are not only the overlay's own layer switches: efficiency switches announce themselves on the bridge through `__moon.perfSwitches()` and are enumerated when a run starts, so one that landed after the overlay was written is swept anyway; a switch found ON is measured by turning it OFF, so its row reads as the cost it removes, and every exact switch that ships on is also measured together as one combined row, because savings that overlap do not add. Per row: rAF callbacks against the wall clock, the main-thread ms inside each frame (`busy`, both ends of the animation loop) and the rest of the frame (`off` — GPU, compositor or a cap). Still slow on the control with an idle main thread means the frame rate is capped from outside the app, which is what iOS does under pressure. Live beside it: the smoothed frame interval the frame-sliced work budgets itself against plus each consumer's budget, spend and queue depth, with a Reset budget button that believes the next frame outright (`frameInterval.resume()`), the same reset returning to a hidden tab performs. The table reaches `?debug=1` through debugLog and `window.__moon.perfSweep`; `__moon.perfRun({mode, keys, blocks, holdMs})` drives a run from a harness and `__moon.perfStop()` ends one, `__moon.perfArmKeys()` lists every key it would offer, `__moon.perfArm(key, on)` applies one by name, `__moon.perfRegister(key, {set, label})` adds one from a module with no registry of its own, and `__moon.perfTargets()` reports every surface a frame is drawn into in device pixels, which is how a resolution switch is proved to have moved the pixels rather than only the renderer's ratio. `__moon.gpuProfile({frames})` (`src/app/devGpuProfile.ts`) is the direct measurement the sweep only infers by subtraction: the GPU milliseconds of one frame per composer pass and per object draw, measured on the device itself — the wait is a one-pixel readback, the only wait that holds on both engines (`finish` is a flush on Chromium and a no-reply message on WebKit; a fence cannot signal inside the task that made it; Chromium's GPU timer on Metal reads whole command buffers and comes out about three times high), so a span carries a floor (a pass that draws nothing reads it) and the per-draw rows are corrected for it as `netMs`. It runs at whatever pose the app is parked at; on a phone, drive it over USB from the Mac (safaridriver) rather than by hand, and profile the phone both cool and after minutes parked — an iPhone throttles its whole chip within two minutes at Earth's shell, and every row reads three times slower, which no per-draw number can show on its own.
- **A data-only service worker runs in prod** (generated into `dist/sw.js` by `tools/swPlugin.mjs` from `tools/sw.template.js`; behavior pinned by `swContract.test.ts`): it caches `textures/`, `stardata/`, `fonts/`, `models/`, `historic/` under content-hash keys and NEVER touches HTML or JS, so app code can't go stale through it — but when diagnosing a device, still check the menu build stamp first (`?debug=1`), and reach for `?nosw=1` if cached data is suspect. Dev is exempt. Those data directories must hold only format-stable opaque assets or pathname-versioned files (`bright-stars.v1.bin` → a format break ships as `.v2`): new app code must never reinterpret an unchanged data pathname.
- **Sector tile sets are addressed by content**: `textures/tiles/<key>/<tier>.<setHash8>/<c>_<r>.webp`, the hash covering the whole set's bytes, written by `tools/gen-tiles.mjs` into `sectorSets.generated.ts` (the app's hashes) and `tiles/sets.v1.json`, so a re-cut set lands on a path nothing has cached. `VITE_TILE_ORIGIN` (empty = same origin) moves tiles to another host; it is read in `texturePolicy.ts` and by `swPlugin` (off Vite's resolved `config.env`, which is what `.env` files reach) for the worker's allowlist — one variable, or the two would drift. Same-origin tiles are ordinary manifest entries with a digest and a `?swv=` key; only tiles from that other host are held by full URL with no digest and no expiry (WebP magic bytes required before one is stored), and pruned once the app stops naming their set. Tiles fail open to the base map, so failures are made loud on purpose: the build throws per named set whose folder is missing from `dist/` when no origin is set, and the first tile that fails warns through `debugWarn`, so it reaches `?debug=1` on a device too.

### Publishing tiles

Sector tile sets are data and ship from their own repo through jsDelivr, not from this one: `node tools/publish-tiles.mjs --root=<tiles root> --repo=<checkout of the tiles repo>` re-hashes every set the root's `sets.v1.json` names against its bytes, copies the new folders in, commits, and prints the `VITE_TILE_ORIGIN=https://cdn.jsdelivr.net/gh/<user>/<repo>@<ref>` the app builds against — it never pushes and never deletes.
`.env.production` pins that origin so a local `npm run build` produces what CI deploys, and a build with an origin set deletes `textures/tiles` from `dist/` and from the worker's manifest — every tile URL points at the host, so shipping the folder too would deploy 45 MB nothing fetches (`public/textures/tiles` stays: it is what a build with no origin ships, and what the asset tests read).
A published path never moves: a folder name is the set's own content hash, so a re-cut set arrives as a new folder and the old sets stay for clients still asking for them (pruning is by hand, and 404s those clients into their base map).
`--dry-run` prints the plan and touches nothing; `--verify-only` checks a root against its own table with no checkout.
