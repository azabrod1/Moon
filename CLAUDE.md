## Build & Development

```bash
npm run dev        # Vite dev server (hot reload)
npm run build      # TypeScript check + production build (dist/)
npm test           # vitest — astronomy + planetarium unit/golden tests
npm run gen:moons  # Regenerate satellite elements + goldens from JPL (--offline uses .moon-data-cache/)
npm run gen:maps   # Regenerate derived texture maps (runs in headless Chromium)
npm run gen:ktx2   # Regenerate the GPU-compressed colour rungs — 23 jobs, 9 UASTC (planets + Earth) and 14 ETC1S (the photo moons); run BY NAME, not --all (bundled basisu; a shipped webp, sharp, or a gen:moonmaps intermediate per job)
npm run gen:tiles -- <job|--all> [--verify | --grey]   # Re-cut sector tile sets + rewrite sectorSets.generated.ts (needs `npm i --no-save sharp@0.35.4`); --grey only checks the one-channel mask sets are grey texel for texel
npm run publish:tiles -- --root=<tiles root> --repo=<tiles repo checkout>  # Copy verified sets into the tiles repo (never pushes)
```

## Architecture

A Three.js WebGL app. The **Planetarium** (`src/planetarium/`) is the app: the full solar system in real units (1 scene unit = 1 AU) on a floating-origin pattern (player stays at scene origin, bodies are offset by the player's position). `src/main.ts` is a thin entry point owning the renderer, composer, cameras, mode switching, and animation loop; each mode is a controller exposing `activate()/deactivate()/update(dt)`. The renderer's tone curve is the switch's to set (`src/app/renderProfile.ts`: Neutral for Look inside, ACES for the rest, applied beside the composer each branch builds) — a mode never writes it for itself, because main caches every mode and disposes none, so a curve set for a mode's life was the app's for the session. `src/interior/` is the Look-inside tool: `data/interiorTypes.ts` is the interior-model schema, `data/models/*.ts` the provisional models (every number sourced; `data/validate.ts` pins the authoring rules and `data/interiorRegistry.ts` answers for every catalog body with a coverage state and a bulk line; a region's only say in how its material is drawn is a small `look` — a hue turn, a saturation and a lightness on its family's palette, `data/artParams.ts` — so a crust reads pale and grey without a palette of its own), `evidenceSummary.ts` the one place the evidence is read into words — a standing per claim from the KIND of evidence (observed, inferred, contested…), never a score; there is deliberately no points rubric anywhere — and `ui/evidenceView.ts` the grouped reader-facing view of a region's evidence, `cutFrame.ts` the cut itself (one quarter wedge through every layer at Cutaway, one disc at Section, chosen from the camera once and locked to the body's pose through a body-space anchor, so orbiting turns the body under it; the wedge is yawed 20° so one face meets the eye, a yaw that fades to nothing as the opening widens to Section, because a disc turned off the camera shows the skin's far half past its edge; "Cut faces the camera" in View options is the old following behaviour and Reset view chooses it afresh), `rendering/skinCut.ts` the discard that removes the skin, the rings, the air shell and the Sun's photosphere inside the wedge — the wedge as the pair of half-spaces its faces bound, linear at the hinge where an angle test left a notch at each pole, and a far-side shell reflected through the plane facing the camera THIS frame, since the wedge does not follow the camera — `interiorPick.ts` the CPU pick that mirrors the wedge the shaders draw, `ruler.ts` the depth ruler's layout through the same remap (one straight line down a face, hidden once both faces turn away) and `ui/DepthRuler.ts` its drawing IN THE PLANE OF THAT FACE (every mark measured along the face's own axes and projected, each label transformed by the face's projected axes at its anchor, so the ruler foreshortens with the face instead of floating over it; the km labels thinned as a series — every second, fifth or tenth tick — with the unit on the deepest, a label dropped from a core too small to hold it, and an annotation bracket drawn only with its name inside the disc; `ui/rulerLabels.ts` holds those rules pure), `interiorTransition.ts` the ceremony's lengths and its order in one place (the entry's opening, a swap's close, the skin's dissolve, the reopen, and whether the cut waits for the veil — it does: activate resolves with the body presented and the cut closed, main lifts the veil onto a frame the studio has actually drawn, and its `transitionend`, or the timer standing in for a lost one, opens the cut, so the whole opening is seen instead of half of it playing behind black), `interiorLayout.ts` the stage-aware framing (the body fitted to the rectangle the strip and the panel leave free — the bound is `InteriorScene.boundRadius`, the body with its air and never its rings, which run off the stage as context — the zoom kept as a ratio to the fit; the fit is taken again once a body is presented, since the air shell's scale is only known then and the Sun's corona reaches 1.3 radii), `temperatureProfile.ts` temperature as a function of physical radius — the ONE sampler the Temperature diagram, the Materials glow, the body's scale, the legend swatches and the inset read, so the two views never disagree about how hot a place is; the faces hold each region's ramp as knots and compute the incandescence per pixel from the local temperature (a star's zones read that place pulled part way to their region's, so they step at their boundaries the way a diagram draws shells), and `rendering/sectionMaterial.test.ts` holds the GLSL to the TypeScript — `temperatureScale.ts` the body-specific scale the faces and the legend share (log when the range is wide; a single known value is a scale of one value, never no scale), `rendering/outputTransform.ts` what the output path does to a diagram face (the exposure, Neutral, sRGB), stated once so the sweep verifies it on the real renderer, `ui/hoverCard.ts` the preview beside a fine pointer, built once and moved by a transform, with the mode keeping a pointer's moves for the frame so a burst is one pick (the card and the mode both cache on its key, so the key carries the body and the model in front of the region — `hoverCardKey` — because a bare region key is shared: a dozen models call their innermost region 'core'), `ui/interiorCopy.ts` the panel's recurring labels, and `ui/InteriorPages.ts` the panel's pages (a pin opens a region's summary; its details, its evidence and the model page are pages of the same host on both breakpoints — the sheet on a phone, the side panel on desktop — with the layer list the page they return to; the rarely touched controls sit behind View options in the strip along the top). Temperatures show in ONE unit, the reader's (kelvin by default, celsius from View options, session-only). In Temperature mode a region whose temperature nobody knows is hatched, never drawn cold, and on desktop says so under its name on the ruler (`ui/interiorCopy.TEMPERATURE_NOT_KNOWN`), so the hatch is never read as a texture. The studio (`InteriorScene.ts`) borrows the planetarium's skins, air shells, rings and the Sun's photosphere (held under the bloom threshold there, over a floor of its own colour, so the core is the one thing that blooms), all cut by the same frame (`rendering/skinCut.ts`); its key is camera-relative from the upper left and the section faces carry a fill of their own inside the shader, from the right and in the key's units, so the face the key misses is lit from its own side and never a scene light the skin would see; a body swap is a ceremony (close, cross-fade in the skin's shader, reveal with a ghost) and `prefers-reduced-motion` stills all of it. `src/moonFlight/` is a dormant lunar-landing mini-game — intact but with no UI entry point. `src/astronomy/` is the ephemeris (Meeus + Standish elements, every planet's moons, analytic shadow/eclipse engine). `src/shared/` holds framework-free helpers (`math/angles` is the single source for `DEG2RAD`/`RAD2DEG`).

**Module headers are the subsystem documentation** — read the header comment before changing a module. Pure logic lives in DOM-free modules with colocated tests; the tightly-coupled per-frame core deliberately stays in `PlanetariumMode.ts`.

Generated / transcribed sources: `src/astronomy/satelliteElements.ts` is generated — edit only via `npm run gen:moons`; `standish.ts` element values are transcribed verbatim — never re-round them. The bright-star catalog ships as `public/stardata/bright-stars.v1.bin` + its golden `brightStarsGolden.json`, both written only by `npm run gen:stars` (parser and store: `src/planetarium/data/brightStars.ts`; consumers read `brightStarCatalog()` only after the boot loader installs it).

**Frame contract: right-handed J2000 everywhere.** The scene is the J2000 equatorial frame as a proper rotation: +X vernal equinox, +Y celestial north, +Z = RA 270°. `raDecToVector` (`planetary.ts`) is the single chirality definition site — never re-inline the formula. Meeus Earth/Moon longitudes (ecliptic-of-date) precess to J2000 at the `planetary.ts` vector seams — never inside `ephemeris.ts` (its goldens quote of-date values). Earth's render position stays Meeus (−Sun vector, precessed) for exact Sun–Earth–Moon coherence. Absolute rotation phase is real (IAU pole + node + verbatim W). All sign conventions are deliberate and test-pinned: don't flip any in isolation. JSON goldens are stored in raw Horizons frames; only the test-side `horizonsToScene` mappings encode the scene convention.

**Lens correction**: the planetarium renders through a stereographic lens pass (`shared/math/lensProjection` + `app/LensPass`), so:

- `applyDesignFov` is the only legal `camera.fov` writer; `camera.fov` holds the overscan — never compare against it, use `displayFovDeg()`.
- On-screen sizes/footprints come from `projectSphereToScreen`; screen-authored GPU primitives pre-distort via `shared/three/lensShader` — never size them from `camera.fov`.
- Every consumer reads `lens.effectiveStrength ?? lens.strength`, never the raw request.
- `tools/oval-probe.mjs` is the asserting regression battery.

### Key patterns

- **All textures bundled locally** in `public/textures/`, referenced via `import.meta.env.BASE_URL + 'textures/'` — such paths are invisible to both tsc and Vite; verify them by running the app.
- **UI is vanilla HTML** in `index.html` (no framework); the TS reads elements by `id` — keep the `index.html` id set and the `getElementById` calls in sync.
- **Nothing half-loaded is ever shown**: a moon never renders before `MoonPainter` finishes it, and teleports hold the arrival veil until the destination is ready. Perf work must preserve this gate.
- **Transient overlays are one-modal-at-a-time** (the ☰ menu, the deck, and the Look-at menu close each other; landing, takeoff, and mode deactivation close them too) — wire new overlays into the same close calls. The tutorial card is the one deliberate exception: the tutorial stages scenes through the other overlays, so only its own buttons and lifecycle close it.
- **UI idioms**: body tints come from catalog `color` (`planetData`/`moonData`), never hardcoded; names render through `bodyDisplayName` (deck rows deliberately show raw catalog names); list rows reuse the deck's `pk-row` family; view sub-states (surface view, orbit details) are session-only. UI copy is plain and human — read the neighbouring strings and match them.
- **The mobile breakpoint is 640px**: test UI changes at desktop and at 390×844 — the narrow band is where overlays collide.
- **Full screen is the page's own request** (`src/app/fullscreen.ts`): the ☰ Full screen row (hidden where `document.fullscreenEnabled` is false) and F in every mode that takes keys, on the document root, so to the app it is only a resize. Escape is the catch: in a full screen the page asked for, the browser spends Escape on leaving it, so on Chromium the module locks Escape with the Keyboard Lock API and the Esc cascade keeps working (leaving is a held Esc, F or the row); Firefox and Safari keep Escape for themselves. Playwright cannot show any of that — its Chromium goes full screen without resizing the window and hands Escape to the page — so a harness (`tools/fullscreen-probe.mjs`) proves the calls, the state and the routing, and a real browser is the only proof of what Escape does.
- Startup URL params: `?auto=volumeCompare` boots the "How many fit?" compare mode; `?auto=interior&body=<name>` boots the Look-inside tool on a body (the Tools row and a map card's Look inside are the in-app doors; every entry goes through `PlanetariumMode.enterTool`, which snapshots the journey so leaving restores it; the tools share `planetarium/ui/BodyPicker`); `?debug=1` shows the error/debug overlay; `?nosw=1` unregisters the service worker and deletes its caches (the kill switch); `?sectors=0` turns off surface sector streaming (Earth/Moon/Mars draw their equirect maps only — the A/B for tile questions); `?synth=0` holds the close-range detail synthesis at zero on every surface (the A/B for what a magnified surface looks like without it); `?ride=0` turns the ride frame off (`src/planetarium/rideFrame.ts`: near a body the ship rides along with it, so a parked ship holds its ground instead of being swept by the body's orbital motion — the A/B for any near-body flight question, and the kill switch); `?orbitanchor=0` poses the orbit lines the old way, heliocentric float32 vertices translated by −ship (`src/planetarium/orbitLineAnchor.ts` measures each line's vertices from an anchor near the ship and re-anchors on a derived drift bound, so a line no longer jumps by hundreds of km as the ship moves — the A/B for an orbit line that moves when the ship does, and the kill switch); `?tilebytes=0` uploads every sector tile straight from its ImageBitmap instead of decoding it to raw bytes first (the A/B for tile-UPLOAD questions — the byte path's whole point is that the driver has no source to convert; it works in prod like `?sectors=0`, because the stutter it addresses was reported from a phone, and `?debug=1`'s memory line plus `__moon.sectors().tilePixels` say which path a device is actually taking); `?canvasaa=1` gives the canvas its own multisampling back and draws the no-float direct path, the System Map and the corner chart straight onto it as before (the kill switch, and the A/B's "before"; a context attribute, so it takes a reload) — by default the canvas has no samples, because on the composer path they smoothed one full-screen quad and their resolve cost a fifth of an iPhone's frame, and those three draws go onto a screen target with the samples they had and are copied across byte for byte (`src/app/screenTarget.ts`; `tools/pixel-gate.mjs --reloadq=canvasaa=1 --poses=map,chart,...` is the proof); `?msaa=0` turns the composer scene target's multisampling off and brings back the old 1.5× supersample floor, i.e. production's rendering before multisampling (the kill switch; policy in `src/app/renderResolution.ts`); `?ratio=<n>` (DEV only) pins the output pixel ratio for the session with the caps and floors ignored — a 3× phone's full panel (`?ratio=3`, the policy caps it at 2) or a 1× monitor's frame on a 2× Mac, as two links to compare from an address bar; the same pin as `__moon.pinRatio`, and the bloom chain keeps the display's own ratio either way; the dev server also takes `?msaa=2|4|8` to force a count on any display (the A/B for antialiasing questions — 4 or 8 on a dense display can exhaust GPU memory, so production ignores them).; `?upscale=<scene ratio>` (any build) draws the planetarium's scene, lens, bloom and tone map at that pixel ratio instead of the canvas's and carries the frame across to the canvas with one resample — AMD FSR 1's EASU and its RCAS sharpen where the scene is smaller than the canvas, an area box average where it is larger (`?downsample=tent`, DEV only, is that average's soft arm) (`src/app/UpscalePass.ts`; the shaders, a transcription of AMD's reference, in `src/app/fsr1.ts`; the two-ratio policy, `renderPixelRatio`, in `src/app/renderResolution.ts`): `?upscale=1.5` on a phone that renders at 2 is 0.5625 of the pixels through the scene and every full-screen pass, and `?upscale=0` pins the canvas's own ratio (the kill switch); a `?upscale=` word is a measurement PIN, so while it stands it owns the scene ratio and the graphics-quality level is held out of the way; the dev server also takes `?upscale=1.5,bilinear` (the control arm: no upscale pass, the finishing pass drawing the smaller buffer straight to the canvas through a linear filter, which is what a browser's stretch of a smaller canvas does) and `?sharpen=<stops>|off` (RCAS, 0 = sharpest, each stop halves; the default of 1 is where the upscaled frame's edge energy matches the native frame's), all live as `__moon.upscale({ratio, sharpen, filter})`; there is deliberately no perf-switch key for the render resolution — the graphics-quality levels are its A/B and a key would be a second writer of the same variable, arming itself on every DEV boot — and `__moon.perfTargets()` reports the scene ratio, the resample's targets and the scene-sized targets' bytes, which is how a run is proved to have drawn fewer pixels rather than only changed a number; `?quality=low|medium|dynamic` (any build) boots at that graphics-quality level — `medium` is the output ratio, today's frame byte for byte, and the kill switch; `?quality=high` is the dev server only, because a production link must not be able to allocate a few hundred megabytes of render target (the `?msaa=2|4|8` line). The same level is the ☰ menu's **Graphics page**: the panel is pages now (`src/planetarium/ui/PlanetariumMenuPanel.ts` — one popover, `.menu-page[data-page]` children of which exactly one is current, a `button.menu-tier[data-open=…]` row on the root opens the page it names and the `‹` button returns, the pages slide and hiding resets to the root; a future tier is markup and nothing else), and the root's "Graphics" row carries the level beside it, under Dynamic as `Dynamic · Medium`. The page holds a segmented control over Low · Medium · High · Dynamic (`src/planetarium/ui/SegmentedControl.ts` wires the static markup; no segment is ever disabled) with a one-line note under it, and a level this display does not offer has no segment at all rather than a choice that would change nothing: High where the machine refuses a supersample (the no-float path, a machine whose GPU completed no multisampled half-float target, a target over the GL size limit, or the byte budget — facts about the machine, never a chassis: no rule asks whether it is a phone), Low where it would collapse onto Medium (the same two paths from the other end). `qualityBounds().highOffered` decides and `.reason` says why; `src/app/graphicsMenu.ts` is the DOM-free rule for the offered list, the notes and the words. Under Dynamic the page also shows "Now rendering": the word for the rung being drawn (Medium, Low, High, or "Between Low and Medium"), a pip per rung with the one in use lit, and the three ends captioned — refreshed from `onScenePixelRatioChanged`, which is admitted onto that hot path behind a guard that returns unless the menu is open ON the Graphics page, because the menu's auto-pause does NOT pin the resolution controller and the rung can move while the reader watches. The level saves on its own localStorage key (`src/app/qualitySetting.ts`, the `hasSeenHelp` shape), never in the journey save, so New Journey and a restore leave it alone; a saved level whose boot never reached a frame is refused on the next one, which takes medium and warns. What the levels mean is `src/app/renderQuality.ts`: Low is 0.75× the output ratio (and never more than the 2× EASU is specified for), High the largest supersample of 1.5× and 1.25× that fits the byte budget and the GL size limit, Dynamic a slide over the rungs between them — below Medium on the 60 fps budget, above it only while the display's own rate holds (the Frame rate paragraph). The byte budget is the risk in supersampling: the scene-sized targets cost 16 B a scene pixel with no samples and 60 B with four (colour, depth/stencil, the resolve, the LDR target; the composer's partner adds 8 B only on the `?fused=0` chain, the one that binds it — three allocates a target on its first bind, so on the chain that ships it costs nothing and is not counted), and they may hold at most 40 % of the device's live texture envelope — which the DEV `?envelope=` shrink reaches too. A level change takes a NARROW path (`applySceneResolution`): the scene-sized targets are pointed at the size the new ratio draws, the resample is re-pointed and the scene-ratio consumers are told, and nothing else is rebuilt — no materials, no passes, no textures — while the sector tiles and the close-range density stay on the OUTPUT ratio so a Dynamic slide can never swap the tiles under the user (the fixed High level is the one exception: it picks its tiles once, for the pixels it really draws). **Dynamic allocates those targets ONCE, at the top rung of its ladder, and draws every rung into a sub-rectangle at their origin** (`src/app/sceneSubRect.ts`): freeing and allocating them is the expensive part of a step — 19–42 ms at a phone frame and 65–150 ms at a Mac window in WebKit, in both directions, whatever the pixel count — so a rung change writes a viewport, a scissor box and three uniforms and moves no memory at all. The price is memory: any display at Medium under Dynamic holds High's allocation at all times — on a 3× phone offered High that is the panel's own 1290×2796, ~58 MB at 16 B a pixel. Only Dynamic, and only the planetarium's composer: Low, Medium and High allocate exactly what they draw (so Medium is today's frame BY CONSTRUCTION), the other modes' composers never do it, and a `?upscale=` pin allocates for itself and hands the allocation back on release. Everything that reads a scene-sized target is scaled into the rectangle and clamped half a texel inside its far edge — the bloom bright pass, the finishing pass, EASU and the box, plus the lens pass's two reads on the `?fused=0` chain (RCAS reads EASU's own output-sized target and keeps its full bounds) — and the region outside it is never cleared and never read. On the shipped chain the bright pass and the finishing pass read through the lens warp, which applies the same scale and clamp inside itself (`lensSourceUv`), so such a site scales exactly once. `applySceneViewports` is the only writer of those three rectangles and runs after every size, because `RenderTarget.setSize` resets them even when the size has not changed; the origin is (0, 0) because the point-sprite kernel and the resample shaders read `gl_FragCoord` as framebuffer-absolute. At boot, under the cover, Dynamic draws one frame at the bottom rung and one at the top before the reveal, so the LDR target, EASU's target and both resample programs are bound and linked where nobody is looking. `?alloc=0` (any build) puts the per-rung re-allocation back: the kill switch, and the A/B for a sub-rect bug on a device that is not here; `?fused=0` (any build) ends the frame in three full-resolution passes again — a lens pass of its own, the bloom blend, then the tone map — instead of the one finishing pass that ships (`src/app/FusedOutputPass.ts`: the bloom bright pass reads the scene image THROUGH the lens warp and the finishing pass does `tonemap( scene(warp(uv)) + composite(uv) )`, so a full-resolution half-float write, read and read-modify-write leave every frame, and on the lens-less composers a second resolve of the multisampled scene target with them). It is the one item that cannot promise exactly the same pixels — the sum of lens and bloom is no longer rounded to fp16 before the tone curve, the bright pass's tap on the scene is one bilinear rather than a bilinear of a bilinear, and that tap can reach half a scene texel into the overscan at a frame corner — so the picture it replaces stays reachable: `?fused=0` is the kill switch and the A/B, in DEV also `?perfoff=fused-final`, and `tools/pixel-gate.mjs --reload=fused-final --report` (with `--poses=…,sun-corner,compare,interior`) is the sheet. `__moon.gpuProfile` names the passes so the two chains' tables line up: `Lens`, `Bloom` and `OutputPass` on `?fused=0`; `Bloom` (now carrying the warp) and `Finishing` on the shipped chain — and a pass that leaves the chain takes a span floor with it, so a per-pass comparison across the two arms overstates the saving unless the floor is quoted beside it. `?fps=screen|30|60|120` (any build) boots at that frame rate — the second control on that same Graphics page, "Frame rate", a segmented Screen · 30 fps · 60 fps · 120 fps with its own note, every value offered on every display, saved on its own localStorage key (`src/app/frameRateSetting.ts`, no boot-loop marker: a target allocates nothing) with the URL winning over the saved value. **Screen is the default and is today's loop by construction**: `ticksPerDraw` is forced to 1 and `due()` returns before any arithmetic, and the resolution controller keeps `BUDGET_MS` at and below Medium. What Screen does hand the controller is the display's own tick, which is what a rung ABOVE Medium is held to: a 120 Hz Mac takes a sharper rung only while 120 fps holds and hands it back to Medium when it does not, and on a display with no finer tick than 60 fps Dynamic never climbs above Medium on its own — the intervals there cannot tell an 11 ms frame from a 16 ms one, and a rule that climbed while frames were on time was measured climbing blind until they missed (a phone at Earth's shell from a locked 60 fps into the fifties and hotter, a 120 Hz Mac from 120 to 80) — so High is the menu's choice there. A row's 30/60/120 is a rate the user asked to be defended with pixels, in both directions. A target is TWO things (`src/app/frameCadence.ts`): pacing — draw every N-th animation callback, N from the request over the delivered cadence, so a stream throttled to half the display's rate draws every callback instead of halving the picture again — and a budget Dynamic then defends with pixels (`max(period, requested)`, so 60 on a 144 Hz monitor delivers 72 but defends 60). The display's cadence is calibrated under the boot cover as a span over its own interval count (never a median, which reads alternating late ticks as a FASTER screen and would slide the picture down), raised live on a window 15 % faster and never lowered, and `?refresh=<hz>` (DEV) pins it so a 60 Hz machine can be asked what a 120 Hz one would do. Under a target the simulation still runs every callback and only the PRESENTATION waits for a drawing one — the label and marker pipelines, the constellations, the Observatory's bracket and reticle, the map's projection ledger, the corner chart, Look inside's ruler — and the holds that open the cap are the perf sweep, a GPU profile and a capture pin (`__moon.quality().fps.held` says which; a boot whose URL named `?fps=` keeps its pacing under a capture pin, because such a run is a measurement OF the pacing and waits on `__moon.waitForDraw` instead). An arrival veil is NOT a hold: it asks for the one painted frame it must show before it lifts and pacing continues under it. `__moon.quality().fps` reports the request, the calibrated and observed cadences, `ticksPerDraw`, the period, the budget, the drawn rate and the capped word; `__moon.drawLog(n)` is the last n draws, which is what `tools/smoothness-gate.mjs --scenario=fps-pacing` reads; `__moon.setFps(rate)` picks a value exactly as the row does, and the row never appears in `__moon.perfSwitches()` — the sweep must not sweep a user's setting. The phone heat claim (halved GPU work when parked, not halved heat) is a USB soak and is not measured here. `__moon.quality()` reports the level, the rung, the bounds, the bytes, the allocation and the decision rule's own window, `__moon.setQuality(level)` picks a level exactly as the menu row does, and DEV `__moon.quality({inject})` feeds synthetic frame intervals straight to the rule, so a browser run can prove a rung moves without faking load — which no pin can do, a pin holding the rule idle by design. `__moon.perfTargets()` answers with `sceneAlloc`, `sceneDraw`, `sceneViewport` per target, `uvScale` and `sceneBytes` from the ALLOCATION, so "did it draw fewer pixels" is read off the draw size and "what is the device holding" off the allocation — and so does the `?debug=1` memory line; `?tiles=<url prefix>` (DEV only) fetches sector tiles from somewhere else — rarely needed now that `npm run dev` also serves the staged levels in the main checkout's `.moon-data-cache/tiles-staging` on its own origin (`tools/devTilesPlugin.mjs`; `MOON_TILES_ROOT` moves the root), so a plain dev URL streams every level; `?envelope=<MiB>` (DEV only) shrinks the shared GPU memory envelope, which is how a desktop is put under a phone's pressure without a phone (the profile's ceiling and sector floor stay put); `?perfoff=<key,key>` (DEV only) boots with those GPU-efficiency switches off (`src/app/perfSwitches.ts` — every switch is an A/B against the picture as it was, flipped live by `__moon.perfArm(key, on)`; this is how one whose state is fixed at upload, `r8-maps`, or at compile, `cloud-program`, is captured in its old state; the four `cloud-probe-*` keys are not switches but probes — each takes one term off the cloud deck so a device can price it, off by default, never exact, and a production build carries neither reading); `?glint=<roughness>[,<keep>[,<cap>]]` (DEV only) draws open water at that GGX roughness for the session, with the mirror term's keep and cap after it — the ocean glint's three authored numbers (`OCEAN_ROUGHNESS`, `OCEAN_SPECULAR_KEEP`, `OCEAN_GLINT_CAP` in `world/surfaceShading.ts`), live as `__moon.glint({roughness, keep, cap})` so a look round is a sheet from one page load rather than an edit per candidate; `?perf=1` (DEV only) raises the on-device perf sweep (`src/app/devPerfSweep.ts`) — an overlay that measures, at whatever pose the app is parked at, what one layer at a time costs. **It is built around a device that heats under its own measurement and caps its frames at 60**: every candidate is measured in A B B A blocks (baseline, candidate held across two windows, baseline) with 2.5 s holds and the first 0.5 s dropped, each candidate hold charged against the baseline hold beside it, and the row shows the median of those pairings with their spread — a spread wider than the median is a device that moved more than the switch did. The order is reshuffled every run and printed, the all-off control sits outside the blocks, and every baseline is printed in sequence as a thermal-drift line (a fixed-order single-pass sweep ranks the order, not the configurations: an iPhone run read the spacecraft at 30 ms, which was the drift). **The load amplifier pins the render ratio to 3 for the run** — a checkbox turns it off — so every configuration sits below the 60 cap, where a 2–4 ms saving has somewhere to show instead of reading 60 either way; the milliseconds are then ratio-3 milliseconds, and the bloom chain sizes from the display's own ratio rather than the pin, so the bloom rows are at their true size. The run is frozen (clock rate 0, restored after; sector tiles waited out before the first hold; a page hidden mid-run — Auto-Lock — stops it on the spot and says so) and the pose is left where it is — the verdict names it (read from the close-range density map, else from the body the ride frame holds, else it says why not), daylight, terminator or night with the Sun's height under the camera, because an early-out that skips work where a term is exactly zero cannot be priced from the wrong side of the terminator. Four runs, each stating its holds and wall time before it starts: **Phone** (the preset — the efficiency switches plus the tile layer, half the pixels and everything-at-once, one block each, about two minutes; the default on a touch device), **Sweep** (every candidate, two blocks each), **Quick** (the older single bracketed pass, A B A C A D at 3 s) and **Soak** (five minutes of baseline logged every ten seconds, which is the only run that can say whether a saving survives sustained load). The candidates are not only the overlay's own layer switches: efficiency switches announce themselves on the bridge through `__moon.perfSwitches()` and are enumerated when a run starts, so one that landed after the overlay was written is swept anyway; a switch found ON is measured by turning it OFF, so its row reads as the cost it removes, and every exact switch that ships on is also measured together as one combined row, because savings that overlap do not add. Per row: rAF callbacks against the wall clock, the main-thread ms inside each frame (`busy`, both ends of the animation loop) and the rest of the frame (`off` — GPU, compositor or a cap). Still slow on the control with an idle main thread means the frame rate is capped from outside the app, which is what iOS does under pressure. Live beside it: the smoothed frame interval the frame-sliced work budgets itself against plus each consumer's budget, spend and queue depth, with a Reset budget button that believes the next frame outright (`frameInterval.resume()`), the same reset returning to a hidden tab performs. The table reaches `?debug=1` through debugLog and `window.__moon.perfSweep`; `__moon.perfRun({mode, keys, blocks, holdMs})` drives a run from a harness and `__moon.perfStop()` ends one, `__moon.perfArmKeys()` lists every key it would offer, `__moon.perfArm(key, on)` applies one by name, `__moon.perfRegister(key, {set, label})` adds one from a module with no registry of its own, and `__moon.perfTargets()` reports every surface a frame is drawn into in device pixels, which is how a resolution switch is proved to have moved the pixels rather than only the renderer's ratio. `__moon.gpuProfile({frames})` (`src/app/devGpuProfile.ts`) is the direct measurement the sweep only infers by subtraction: the GPU milliseconds of one frame per composer pass and per object draw, measured on the device itself — the wait is a one-pixel readback, the only wait that holds on both engines (`finish` is a flush on Chromium and a no-reply message on WebKit; a fence cannot signal inside the task that made it; Chromium's GPU timer on Metal reads whole command buffers and comes out about three times high), so a span carries a floor (a pass that draws nothing reads it) and the per-draw rows are corrected for it as `netMs`. It runs at whatever pose the app is parked at; on a phone, drive it over USB from the Mac (safaridriver) rather than by hand, and profile the phone both cool and after minutes parked — an iPhone throttles its whole chip within two minutes at Earth's shell, and every row reads three times slower, which no per-draw number can show on its own.
- **A data-only service worker runs in prod** (generated into `dist/sw.js` by `tools/swPlugin.mjs` from `tools/sw.template.js`; behavior pinned by `swContract.test.ts`): it caches `textures/`, `stardata/`, `fonts/`, `models/`, `historic/` under content-hash keys and NEVER touches HTML or JS, so app code can't go stale through it — but when diagnosing a device, still check the menu build stamp first (`?debug=1`), and reach for `?nosw=1` if cached data is suspect. Dev is exempt. Those data directories must hold only format-stable opaque assets or pathname-versioned files (`bright-stars.v1.bin` → a format break ships as `.v2`): new app code must never reinterpret an unchanged data pathname.
- **Sector tile sets are addressed by content**: `textures/tiles/<key>/<tier>.<setHash8>/<c>_<r>.webp`, the hash covering the whole set's bytes, written by `tools/gen-tiles.mjs` into `sectorSets.generated.ts` (the app's hashes) and `tiles/sets.v1.json`, so a re-cut set lands on a path nothing has cached. `VITE_TILE_ORIGIN` (empty = same origin) moves tiles to another host; it is read in `texturePolicy.ts` and by `swPlugin` (off Vite's resolved `config.env`, which is what `.env` files reach) for the worker's allowlist — one variable, or the two would drift. Same-origin tiles are ordinary manifest entries with a digest and a `?swv=` key; only tiles from that other host are held by full URL with no digest and no expiry (WebP magic bytes required before one is stored), and pruned once the app stops naming their set. Tiles fail open to the base map, so failures are made loud on purpose: the build throws per named set whose folder is missing from `dist/` when no origin is set, and the first tile that fails warns through `debugWarn`, so it reaches `?debug=1` on a device too.

### Publishing tiles

Sector tile sets are data and ship from their own repo through jsDelivr, not from this one: `node tools/publish-tiles.mjs --root=<tiles root> --repo=<checkout of the tiles repo>` re-hashes every set the root's `sets.v1.json` names against its bytes, copies the new folders in, commits, and prints the `VITE_TILE_ORIGIN=https://cdn.jsdelivr.net/gh/<user>/<repo>@<ref>` the app builds against — it never pushes and never deletes.
`.env.production` pins that origin so a local `npm run build` produces what CI deploys, and a build with an origin set deletes `textures/tiles` from `dist/` and from the worker's manifest — every tile URL points at the host, so shipping the folder too would deploy 45 MB nothing fetches (`public/textures/tiles` stays: it is what a build with no origin ships, and what the asset tests read).
A published path never moves: a folder name is the set's own content hash, so a re-cut set arrives as a new folder and the old sets stay for clients still asking for them (pruning is by hand, and 404s those clients into their base map).
`--dry-run` prints the plan and touches nothing; `--verify-only` checks a root against its own table with no checkout.
